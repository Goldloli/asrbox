# Proposal: translation-output-sanity-guard

## 为什么

`translation-local-retry-hardening` 解决了本地 Ollama 翻译的超时与结构校验失败，但真实用户实测（qwen3.5:9b，137 段校对版字幕）暴露出更深的失败模式：结构校验通过、内容却是错的。小参数本地模型在大批次结构化输出下会"应付"schema——把整段字幕的连续译文切成滑窗片段填入各目标段：

- 137 段任务 32 段译文超过原文 3 倍长度，相邻译文共享 25+ 字符的公共子串（译文互相重叠覆盖），用户看到"原文一句话、译文一大段""译文不对应"。
- 本机对照实验（真实提示词 + 真实数据 + 本机 Ollama）：76 段批结构校验直接失败；38 段批 6 段膨胀 + 相邻重叠（输出总量 1.9 倍于英文原文，正常应 0.5-0.7 倍）；19 段及以下完全干净（0.45 倍、零重叠、7 秒返回）。

结构校验（ID 恰好覆盖、文本非空）无法发现这类内容错位，脏数据会持久化为检查点。现行 100 段/6000 字符的初始批次上限对小本地模型过大，既诱发该行为，也让单请求延迟高达数分钟。

## 变更内容

- 初始批次上限按提供商协议区分：本地 Ollama 原生协议 16 段/1600 字符，其余协议保持 100 段/6000 字符（续译沿用持久化批次边界，不受影响）。
- 解析通过后新增内容合理性校验：任一相邻译文共享 ≥25 字符公共子串（滑窗特征），或整批译文总量 >2.2 倍源文总量且超出 200 字符以上（异常膨胀），视为未通过校验，与 TRANSLATION_INVALID_RESPONSE 走同一确定性对半拆分路径；单段结果不再拆分，直接接受。
- 系统提示词补充目标隔离要求：每条译文只翻译对应目标段，不得包含上下文或其他目标段内容，长度应贴近源段。
- 既有语义保持不变（非目标）：结构校验规则、拆分有界递归、子批不单独成为持久化检查点、已成功批次不重发、完整结果原子发布、不做内容正确性的全自动保证（校验启发式只驱动拆分，不篡改模型文本）。

## 能力（Capabilities）

### New Capabilities

（无）

### Modified Capabilities

- `transcript-translation`: "有界分批"按提供商协议区分初始批次上限；译文校验在结构校验之上增加内容合理性启发式（相邻重叠、总量膨胀），未通过时走同一确定性拆分路径。

## 影响

- `backend/services/translation.py`：`make_batches` 增加按协议的上限；新增内容合理性检查接入 `_translate_batch` 拆分路径；`SYSTEM_PROMPT` 增加目标隔离句。
- `backend/tests/test_translation_execution.py`：新增滑窗重叠→拆分后完成、总量膨胀→拆分、单段接受、Ollama/非 Ollama 初始批次上限断言用例。
- `openspec/specs/transcript-translation/spec.md`：两条 requirement 的措辞与 scenario 更新。
- 前端翻译等待/超时文案的 90/300 秒显示随本 change 一并修复（UI 此前硬编码 90 秒，与已归档的按协议时限不一致）。
