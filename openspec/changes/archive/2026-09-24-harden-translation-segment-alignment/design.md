# Design: harden-translation-segment-alignment

## 背景

动机与复核数据见 `proposal.md`。设计相关的现状约束：

- `backend/services/translation.py:33-34` 的 `LOCAL_MAX_SEGMENTS = 64` / `LOCAL_MAX_CHARACTERS = 6000` 与主 spec `有界分批和真实进度` 的 16 段/1600 字符冲突；该偏离由 `fbb2c59`（归档 change `align-ui-with-approved-renderings`）引入，同一提交还把本地响应格式改为紧凑有序字符串数组（`provider_response_schema` / `parse_provider_translations`）。
- `_content_misaligned`（`translation.py:228-246`）是唯一的内容层防线，三个阈值都按英文长度标定：`OVERLAP_MIN_CHARS = 25`、`OVERLAP_SOURCE_MARGIN = 12`、`BLOAT_RATIO = 2.2` + `BLOAT_MIN_EXTRA_CHARS = 200`。命中后调用既有 `split_and_retry()`。
- 复核实测的中文漂移串长度为 9–14 字符，因此 `OVERLAP_MIN_CHARS = 25` 是这次漏判的直接原因；`parse_translations` / `parse_provider_translations` 只做结构校验（`translation.py:168-225`）。
- 既有拆分语义（spec `有界分批和真实进度`）：对半拆分、递归至单段、子批不单独成为持久化检查点、单目标不再拆分。
- **两轮对照实验（55 次真实运行，`qwen3:4b` 与 `qwen3.8:27b-mtp-bf16`，合成跨词 fixture）**给出三条改变设计的事实：
  1. **批次大小不是漂移主因**：按本设计四条判据回查第一轮，`local16` 发布版本仍带漂移 **7/11**（4B/40 段 1/5、4B/137 段 3/3、27B/40 段 2/2、27B/137 段 1/1），`local64` 为 8/11，两者相差无几；归档设计"≤19 段干净区间"的结论在今天的 fixture/模型上不成立。
  2. **固定开销接近零**：4B 0.041 s/请求、27B 2.195 s/请求；成本几乎线性于总段数（4B 0.075 s/段、27B 0.499 s/段）。`local64` 只在"段数刚好放得下"时快 7–10%，137 段上反而慢 2.06×（拆分重译的重复劳动）。"大批次省 prompt/schema 开销"不成立。
  3. **漂移的机制是边界**：判定只在单批响应上求值时，拆分边界与跨已保存批次之间是盲区——4B/137 把 64 段批拆成 32+32 后，第 31 段与第 34 段的重复被 32‖33 分界线隔开，两半各自"看起来干净"。批内作用域 180 条命中中，有 11 条**结构上**只能在发布前的完整版本上看见（分布在 8 个 run）。

## 目标 / 非目标

**Goals:**

- 让"结构合法但跨段错位"在**两个作用域**上都可检出：批内命中复用既有确定性拆分路径，发布前命中由新增的定点重译兜底；两者都不改写模型文本。
- 判据按译文长度归一化（不依赖文字系统的绝对字符数），并在 55 次真实运行的语料上标定到**零误报**。
- 让代码重新符合主 spec 已接受的本地批次上限；该上限的依据由实验数据决定（拆分次数与总耗时），不再宣称"干净区间"。
- **在提高精度的同时不牺牲可用速度**（本 change 的验收口径）：精度以发布版本按四条判据零命中为准（现状基线 8/11 命中）；速度要求长字幕（≥100 段）不超过现状 1.5×、短字幕（≤40 段）绝对增量 ≤5 秒，且不慢于同等精度的大批次方案（实验基线便宜 2.0–2.8×）。
- 用合成 fixture 固定住实测漂移形态与必须零误判的反例。

**Non-Goals:**

- 不引入语义级校验（回译、嵌入相似度、LLM 判分）：与"后处理不得依赖外部服务"的既有边界冲突，仍是归档设计中的非目标。
- 不承诺逐段语义正确；纯位移（内容整体前移、无重复、无异常长度变化）不属本设计可检出的范围，作为已知限制记录。
- **不覆盖 echo／未翻译、模型元评论、占位符（实验称 R5 类）**：实验证明归一化重叠、重复渲染、退化填充、膨胀四条判据在结构上看不见它们（echo 的各段彼此互不相同，凑不出重复组；元评论措辞各异），而语料里确有 4 次运行带这类污染。它们是与本 bug 不同的失败类别，需要各自的标定语料与 spec 场景，本 change 只记录、另开任务，不并入本次 diff。
- 发布前的定点重译是**有界一次**的修复手段，不承诺把命中段修成语义正确：实验中出现过"重译后不再触发规则、但内容仍与邻段重叠"的案例，如实记录为限制。
- 不恢复逐段 ID 的响应格式、不改动 `provider_response_schema` 与紧凑数组解析：格式变更不是本 bug 的成因（模型即使标注正确 ID 也可能写错文本），且回退会丢掉该提交的性能收益。此偏离另行记录，不并入本次 diff。
- 不改结构校验规则、检查点持久化模型、拆分递归上限语义与运行生命周期。

## 决策

### 1. 恢复本地初始批次上限 16 段 / 1600 字符

`LOCAL_MAX_SEGMENTS = 16`、`LOCAL_MAX_CHARACTERS = 1600`，与主 spec 及归档设计一致；其余协议仍为 100 段/6000 字符，`saved_batches` 续译沿用持久化边界不变。

备选方案：

- **保持 64/6000，只靠新判据拆分**。否决（有实验数据）：判据一旦生效，`local64` 的"少发请求"优势就消失了——4B/40 的请求中位 5 vs 5、4B/137 为 17 vs 17；拿到零漂移结果的期望耗时 `local64` 比 `local16` 贵 **2.8×**（40 段 13.90 s vs 5.01 s）与 **2.0×**（137 段 49.74 s vs 24.54 s），27B/137 的 `local64` 唯一一次还不干净。原因是检测驱动拆分后，首轮大批次会炸成多次请求。
- **只调小字符上限、保留段数上限**。否决：段数与字符数都被 spec 同时约束，且 40 段/约 900 字符的实测批次仍漂移。
- **把上限做成用户可调设置**。否决（有实验数据）：所谓"速度收益"只存在于"段数刚好放得下"的格子（快 7–10%），长字幕上反而更慢；而可调开关的代价是**73%（8/11）的 `local64` 运行把漂移当成功发布**。速度差来自拆分次数而非批次大小，因此这个开关既买不到速度、又卖出正确性。
- **保持现状的 64/6000 并放弃检测**（即真实的速度优先）：否决，理由同上。

代价：137 段初始请求数由 3 增到 9。按实测逐请求成本（4B 0.041 s/请求 + 0.075 s/段、27B 2.195 s/请求 + 0.499 s/段），固定开销部分约 +13 s（27B/137 实测 +11%），换来的是更少的拆分次数与更早收敛（27B/137：119.35 s 得到干净结果，`local64` 155.49 s 仍不干净），并让 `有界分批` 重新符合 spec。

### 2. 内容合理性启发式改为长度归一化判据（语料标定）

`_content_misaligned` 保留函数位次与调用点（`translation.py:306`），内部改为四条归一化判据，命中任一即返回未通过。阈值在 55 次真实运行的语料上标定为**零误报**（同时保持对已知真漂移的全覆盖）：

1. **相邻滑窗重叠（归一化 + 相对余量）**：`shared >= max(6, 0.6 * min_len)` 且 `shared - source_shared >= max(3, 0.4 * min_len)`。第一版把余量留成绝对 12，实测**全程 0 命中**（`该项目由联邦资金支持`：`shared=10`、`source_shared=2`，`10 > 2+12` 不成立）；改成相对量后语料 32 条命中，人工核对全部为真漂移。注意：语料中最低的真漂移余量恰为 3，紧贴门槛，换模型/语系时需重新标定。
2. **批内重复渲染**：同一归一化译文出现在两个及以上段位，且源文互不相同（归一化后不相等，最长公共子串不足较短源文的 0.8）。文本长度下限由 6 降到 **4**（`该资助项目`、`实验室项目` 这类 4–5 字重复正是漂移形态），语料 34 条命中全部为真。
3. **退化填充**：只在可确认的退化形态上命中——单字符输出（`了`/`a`/`}`）、非 CJK 的单字符重复（`33`/`zzz`）、纯数字或转义填充（`\n`）、去边标点后为空（`。`），并要求源文长度 ≥15。第一版"≤2 种不同字符且长度 ≥2"在中文上把合法的两字词全部误判（`每次`/`所以`/`样品`/`三月`…共 30 条），抬高门槛后这 30 条误报被逐一移除、真形态全部保留。
4. **异常膨胀**：保留全局式（总量 >200 + 2.2×源文总量），并新增**逐条式**（单段输出 >200 + 2.2×该段源文，覆盖"一段吐出一大段 `（Note: …` 元评论"的形态）。全局式在语料上 0 命中，逐条式 4 条命中且均为真。

为什么这样切：判据 1 覆盖滑窗错位，2 覆盖末段重复／整段回卷／跨段复用，3 覆盖退化填充，4 覆盖尾部膨胀——正是实测到的四类漂移形态；四者都只看批量层面的集体特征，不评判单段语义。

备选方案：

- **只把 25 改成 8**。否决：只解决短串阈值，纯位移与退化填充仍然漏判，且长行会变得过于宽松。
- **逐段长度比开方归一**。否决：碎片段与紧凑语系会误伤（归档设计已否决同类方案）。
- **把判定做成模型自检**。否决：额外调用、非确定性、违反既有边界。

### 3. 判据在两个作用域上求值，批内驱动拆分，发布前驱动定点重译

实验证明只做批内判定会留下结构性盲区：拆分边界（32‖33）与跨已保存批次之间，重复内容被"分界线"隔开，两半各自通过（批内 180 条命中中有 11 条只能在完整版本上看见，分布在 8 个 run）；跨批的全局膨胀在单批内甚至无定义。因此：

- **批内作用域**（`translation.py:306`，现状位次）：命中 → 既有 `split_and_retry()`，与 `TRANSLATION_INVALID_RESPONSE`、截断、超时同路；单目标批继续直接接受（`len(parsed) < 2` 早退），递归至单段为止。
- **发布前作用域**（新增，`execute_run` 组装完整结果之后、写版本之前）：对全部目标段整体求值同一套判据。命中时**不**发布，先对命中段做**一次有界的定点重译**（把命中段作为单段批次、带前后邻段上下文，走既有提供商调用路径），复验通过后发布；仍命中则以明确错误码失败并保留既有检查点，不产生可导出的半成品。选择"定点重译 + 失败兜底"而非直接失败，是因为实验里 2 个真实命中案例都在 **1 轮内收敛**且成本极低（4B 每段约 0.9 s，相对整轮 17–33 s 可忽略）；选择"仍命中则失败"而非"发布并告警"，是因为验收条件是"每段译文对应当前源段"，发布带漂移的结果等于把本 bug 原样留下。

例外：**整批膨胀**在发布前命中时不做定点重译——该判据没有可单独修复的命中段（它的判定对象就是整份译文），因此直接失败并保留检查点。定点重译本身也有预算（命中段数超过上限即直接失败），因为成片塌陷逐段重译会发出与整轮同量级甚至更多的请求，而且实测里可修复的漂移都是局部形态（2–5 段）。同理，重复渲染判据的两两比较只探测每个重复组的前 64 个成员，避免超长字幕上出现 O(k²) 的卡顿。

**付费协议不自动重译**：本地 Ollama 之外可能按次计费的协议，首次运行命中发布前校验时直接失败、不发出任何额外请求，只有用户显式续译（`attempt > 1`）后才执行同一有界定点重译。理由有两条：用户文档承诺"失败、取消或重启中断后……不会自动付费重试"（`docs/ai-proofreading.md:86`），自动重译会违反它；而若改成"永不重译"，续译会把已完成的批次直接组装、同样的漂移再次命中、再次失败，形成一个用户永远拿不到结果的死循环。把重译挂到用户显式动作上同时解决这两点：本地免费所以立即自动，线上付费所以由用户点头。备选方案：**三种协议一律自动重译**（最简单，但要放宽对外承诺）；**三种协议一律不自动重译且续译也不重译**（用户只能新建一次翻译，代价是"改两段就好"的便利完全失去）。落地的验收测量里出现过一轮"定点重译后仍命中"的真实案例（4B/40 段，5 次中 1 次），说明失败兜底不是理论条款；这类运行不再发布错位字幕，而是明确失败、保留检查点、可重试。

实现上把判定拆成可独立测试的纯函数（输入段序列与源文，输出命中集合），既服务批内布尔判定，也服务发布前的命中定位与定点重译。

### 4. 回归测试：确定性单测为主，真机测试可选

- `backend/tests/test_translation_execution.py`：按现有 `mock_transport` 模式新增用例——漂移形态（末段短句重复、整段回卷复用、退化填充、逐条膨胀）各断言"触发拆分并在子批完成后发布正确译文"；零误判反例（重复台词行（源文相同）、高频短译文、合法两字词）各断言"不拆分、一次通过"；再加"发布前作用域"用例：构造只在跨批次／跨拆分边界上可见的重复，断言定点重译后发布、以及仍命中时以明确错误码失败且不写版本。
- `backend/real_tests/`：新增合成跨词 fixture 的真机用例，沿用 `ASRBOX_RUN_REAL_MODELS=1` 门禁（与 `npm run test:backend:real-models` 一致），只断言确定性可判定的事实：运行完成、每段非空、已发布版本不含可检出漂移。纯位移与 R5 类（echo／元评论／占位符）不可检出，使该断言在理论上可能偶然失败，因此在设计中记录为已知抖动，并保持其 opt-in、不进 CI 门禁；本机缺少可用本地提供商时按能力探测明确跳过。
- 断言依据的 fixture 全部合成（英文连续叙事按词切段 + 跨句边界），不含任何用户字幕。

## 风险 / 权衡

- [归一化判据误判导致多余拆分／重译] → 代价仅为额外请求与一次定点重译，结果仍正确；单目标总是接受，定点重译有界一次，不会死循环。零误判反例用例覆盖重复台词行、高频短译文、合法两字词三类。
- [阈值是手工标定的，换模型/语系可能失准] → 语料中最紧的一例（真漂移余量 3 vs 门槛 3）已在设计里点名；标定方法与语料形状随 change 留档，换模型时按同样方法重标；门槛失准的表现是多余拆分（慢）而非错判发布（错），方向是安全的。
- [定点重译"收敛但没修好"] → 实验中已出现"重译后不再触发规则、内容仍与邻段重叠"的案例；这是启发式上限，如实记录为限制，并在界面上依赖既有"分享前请检查含义、人名和术语"提示。
- [发布前失败让长字幕白跑] → 只在定点重译后仍命中时失败，且保留既有检查点；实测命中率 7/22 且全部能在 1 轮内修好，失败是兜底而非常态。
- [本地批次变小延长长字幕翻译] → 实测固定开销极小（4B 0.041 s/请求、27B 2.195 s/请求），且 `local16` 拿到干净结果的期望耗时优于 `local64`（4B/40 段 5.01 s vs 13.90 s、4B/137 段 24.54 s vs 49.74 s）；批次边界仍持久化、续译不重切。
- [真机用例随机抖动] → 只断言确定性可判定的事实，保持 opt-in 且不参与 CI/发布门禁；抖动来源在设计中显式记录。
- [仍存在不可检出的漂移] → 纯位移（无重复、无异常长度）与 R5 类（echo／元评论／占位符）都不可检出，前者是本设计的已知上限，后者另行开任务跟踪；界面上"分享前请检查含义、人名和术语"的既有提示仍是最后一道人工防线。
- [阈值调整影响既有滑窗用例] → 现有 `test_sliding_window_batch_splits_deterministically_and_completes` 的共享串 26 字符、邻居文本约 33 字符，仍满足新判据（26 ≥ max(6, 0.6×33)），断言不变。

## 回滚

行为改动集中在 `backend/services/translation.py` 的两个常量与一个判定函数，加上测试与 spec 措辞；无数据迁移、无新依赖、无 API/持久化结构变化。需要回滚时恢复常量与函数体即可，已发布的译文版本与既有运行不受影响（判定只作用于新运行的新批次）。真机用例与单测均为新增文件/用例，删除即回到当前状态。

版本号提升（0.3.4）只改版本元数据与发布材料（`CHANGELOG.md`、`docs/releases/v0.3.4.md`、各版本文件与 lock），不参与上述行为回滚：它由 `npm run version:bump` 机械生成，回滚方式是按同一脚本反向提升版本，与翻译修复的正确性互不依赖。是否 commit、打 tag 或发布不属本 change 的实施范围。
