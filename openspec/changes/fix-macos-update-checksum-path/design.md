## 背景

参见 [proposal.md](proposal.md) 的“为什么”。当前 `tauri/src-tauri/src/update.rs:739` 的 `parse_checksum` 以 Release API 返回的安装包 basename 做精确匹配，这是有意的信任边界。问题出在 `.github/workflows/release.yml:155` 和 `.github/workflows/release.yml:248`：两个构建任务都把带 `./` 的 glob 传给哈希工具，工具因此把该前缀写入分平台清单，publish job 又原样合并。`scripts/verify-release-assets.sh:52` 之后只用子串搜索确认名称存在，并调用能解析 `./` 的系统哈希工具，所以没有验证桌面更新器与清单之间的格式 contract。

截图表明 v0.2.1 的 macOS DMG 与 Windows NSIS 均受影响。仓库内修复只能保证后续构建；已经运行的 v0.2.0 客户端不会获得新代码，因此当前 Release 还需要一次受控的清单资产修正。

## 目标 / 非目标

**目标：**

- 全部平台资产汇总后生成唯一、稳定、仅含 Release 根目录 basename 的最终清单。
- 发布前验证清单格式与桌面更新器的精确匹配约束一致，并用聚焦单元测试覆盖失败样例。
- 以不绑定具体版本号的兼容性 fixture 证明上一受维护版本客户端的解析 contract 能消费下一版本 Release。
- 在不改安装包字节和摘要的前提下，给出 v0.2.1 清单修正、验证与回滚流程。

**非目标：**

- 不让桌面更新器接受 `./`、目录路径或更宽松的清单格式。
- 不改变 GitHub 信任域、资产命名、SHA-256 算法、下载目录或手动安装行为。
- 不重建 v0.2.1 的 DMG、NSIS、FFmpeg 源码包或 CUDA 套件，也不在没有明确授权时修改 GitHub Release。

## 决策

### 1. 在 publish job 集中生成唯一清单

macOS、Windows 与 CUDA kit 任务只上传各自的发布资产，不再生成或上传分平台 checksum 片段。publish job 汇总全部资产后，在 `release-assets` 目录中按确定性顺序把显式 basename 传给同一个 SHA-256 工具，一次生成最终 `SHA256SUMS.txt`。这样只有一个清单生产点，不再依赖不同平台工具输出的合并结果，也不会依赖事后文本替换。

备选方案是让 Rust 解析器剥离 `./`。该方案无法修复已经安装的 v0.2.0，并会扩大客户端接受格式，因此不采用。

另一个备选方案是保留三个分平台清单、只把 glob 改为不带 `./`。它能修复当前问题，但继续保留多套生产路径和跨平台格式漂移风险，不符合长期只维护一个 contract 的目标，因此不采用。

### 2. 用可复用的清单格式校验器连接生产门禁与自动测试

新增无第三方依赖的 Node 发布工具，读取 `SHA256SUMS.txt` 并验证：每行是 64 位十六进制摘要加规范 basename；名称不含 `/`、`\\`、`.`/`..` 路径语义或空白；名称唯一；调用方要求的 DMG、NSIS 及其他发布资产各有且仅有一条。`scripts/verify-release-assets.sh` 在执行实际文件哈希校验前调用该工具。对应 `scripts/*.test.mjs` fixture 覆盖规范的 macOS/Windows 条目、两个平台当前的 `./` 回归样例、目录路径、非法摘要、重复/缺失条目；另以动态的当前版本和下一版本资产名模拟上一受维护客户端解析下一 Release，测试不写死具体产品版本号并自动纳入既有 `test:release-tools` 聚合命令。

备选方案是在 Bash 中追加 `grep`/`awk`。这能减少一个文件，但难以在不复制命令的情况下覆盖失败 fixture，也更容易再次出现“子串存在但客户端不可解析”的偏差，因此不采用。

### 3. 用 Rust 测试锁定客户端现有严格边界

扩充 `parse_checksum` 的单元测试，同时覆盖 DMG 和 NSIS basename 成功、`./` 或其他路径前缀失败、摘要格式失败。运行时代码不需要改变；测试用于证明修复落在 producer，而不是意外放宽 consumer。

### 4. v0.2.1 只替换校验清单资产

获得明确发布授权后，先下载并保存当前 `SHA256SUMS.txt`，将每个条目与同 Release 的资产名称逐一对应，把 macOS 的 `  ./文件名` 和 Windows/MSYS 的 ` *./文件名`/` *文件名` 统一规范化为 `  basename`，保持所有摘要不变。用新的格式校验器和系统 SHA-256 校验（对实际下载的发布资产）验证后，只替换 v0.2.1 的 `SHA256SUMS.txt`，再从 GitHub Release API 重新下载并确认 DMG/NSIS 均能以精确 basename 找到。不得重新上传或改名安装包。

若当前环境不适合下载全部大型资产，发布替换前至少必须核对旧清单到新清单只有名称规范化差异，并对 DMG 与 NSIS 实际文件重新计算摘要；CUDA 大文件继续以已有发布摘要和资产名称做清单一致性核对。此限制必须在执行报告中明确记录。

## 风险

- [替换同名 Release 资产可能经过 CDN 缓存] → 替换后从 Release API 获取新的 asset URL 并重新下载验证；客户端每次检查都重新读取 Release 元数据。
- [格式门禁过严而拒绝合法的系统哈希输出] → 生成任务统一使用文本模式的标准双空格格式，fixture 同时覆盖 macOS `shasum` 与 GNU `sha256sum` 的实际输出形式。
- [测试只证明某个固定版本而不能保护未来版本] → fixture 动态构造相邻版本及两个平台资产名，断言的是稳定命名和解析 contract，不绑定发布版本号。
- [只修仓库而未恢复当前 v0.2.1] → 将 Release 资产修正作为独立、需授权的上线任务；未执行时不得声称截图中的现有客户端已恢复。
- [清单替换时误改摘要] → 对比新旧清单，强制摘要 multiset 完全一致，只允许把校验工具的二进制标记/前导 `./` 规范化为双空格分隔的 basename。

## 回滚

- 代码回滚：恢复两个 workflow 哈希命令及发布格式校验调用；这不会影响已发布安装包，但会重新引入后续 Release 风险，因此只用于定位门禁故障。
- v0.2.1 资产回滚：保留替换前清单副本和 GitHub asset 元数据；若替换后验证异常，重新上传原清单并立即停止应用内下载，引导用户使用浏览器手动下载和校验。回滚会恢复已知故障，只作为短时止损。
